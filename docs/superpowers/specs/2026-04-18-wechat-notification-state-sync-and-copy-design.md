# WeChat 通知状态同步与文案修订设计

## 背景

上一轮已经收口了几件重要事情：

1. `/allow <handle>` 只会命中目标 permission request / notification，不再串批。
2. question 的 mixed reply 语义已经稳定，`multiple + custom=true` 支持编号 + 自定义补充，且带空格编号输入也能正确解析。
3. `/status` 已经改成结构化 todo + checklist 风格，question / permission 文案也比早期清晰。

但微信交互面仍然有几类明显缺口，而且它们本质上属于同一条“**状态同步正确性 + 可操作文案**”问题线：

1. **复制体验不够好**
   - 现在的 `/reply ...`、`/allow ...` 示例仍可能和解释文字混在同一行。
   - 微信里长按通常是整行选中，示例如果不单独占一行，复制成本会偏高。

2. **question 选项信息不完整**
   - 很多 question 的每个选项除了标题，还有对应说明文字。
   - 当前微信通知里往往只显示选项标题，没有把说明一起带上，导致用户离开电脑后很难判断该选哪项。

3. **电脑端终结后，微信侧状态不同步**
   - 如果某个 question / permission 已经在电脑端处理完，微信侧旧 qid / handle 仍可能继续挂着。
   - 用户之后再在微信回复，会得到“已回复问题”一类误导性成功提示，虽然目标 request 实际已经不存在。
   - 更严重的是，微信侧还不知道**为什么**这个入口被回收：是电脑端已回复、已拒绝、已过期，还是被 recovery / cleanup 替代。

4. **Agent 自然中止没有形成可操作闭环**
   - Agent 正常工作流自然停止时，微信侧目前没有一条清晰的通知说明它为什么停、接下来用户能做什么。
   - 用户希望这类事件允许直接发送一条自定义回复，继续给出下一步指令或补充信息。

5. **retry / error 通知缺少错误摘要**
   - 现在 retry 通知往往只告诉用户“有问题”，却没有把关键错误细节带到微信。
   - 等用户回到电脑前，很多上下文已经过去了，通知价值被削弱。

这次设计不把这些点拆开单做，而是统一收成一条“**微信通知状态同步与文案修订**”线：让微信通知既和真实运行态同步，又真正具备离开电脑也能操作的可读性。

## 目标

1. 所有 `/reply ...` / `/allow ...` 示例在微信里都单独占一行，便于长按复制。
2. question 选项如果有说明文字，微信通知必须同时展示“标题 + 说明”。
3. 电脑端终结 question / permission 后，微信侧旧 qid / handle 必须退出可回复集合，并补发终结结果通知。
4. 用户在微信侧继续回复已终结 qid / handle 时，必须拿到稳定的“已结束”提示，而不是误导性成功提示。
5. Agent 自然中止要变成一条**可回复通知**，允许用户直接给出自定义补充。
6. retry / error 通知要携带足够可用的错误摘要，但不直接暴露冗长堆栈或敏感字段。

## 非目标

1. 不重做 broker owner / replacement / runtime failure mode 这条线。
2. 不重做整个微信通知系统的数据模型，更不引入新的复杂状态机。
3. 不新增按钮式交互或微信侧富组件能力；继续沿用 slash 文本交互。
4. 不扩 release/install/debug bundle 相关流程。

## 方案选择

### 方案 A：一体化收口状态同步 + 文案表达

做法：

1. 在现有 question / permission / session-error / retry 链路上统一补“微信可操作性合同”。
2. 一次收口复制体验、选项说明、电脑端终结回收、自然中止可回复、retry 错误摘要。

优点：

- 用户感知是一致的：不会出现一半通知已经可操作、一半还是半成品的割裂状态。
- 电脑端终结、微信回收、终结原因提示、自然中止回复，都是同一套“微信通知要和真实状态同步”的问题。
- 可以避免重复改 formatter / notification store / replyability 判断。

缺点：

- 会同时触达 formatter、候选生成、终结态同步和 slash handler 几条链。

### 方案 B：先 correctness，后表达

做法：

1. 先只修“电脑端终结后微信回收”“自然中止可回复”“retry 错误摘要”。
2. 把示例换行和 question 选项说明留到下一轮。

优点：

- 范围更保守。

缺点：

- 这轮用户最直接看到的文案痛点还会继续存在。
- formatter 层很快还要再改一次，容易重复返工。

### 方案 C：先统一通知模型，再改用户可见行为

做法：

- 先把 question / permission / retry / session-error 的数据结构和 replyability 状态机整体重构，再做文案和交互。

优点：

- 从架构上最整齐。

缺点：

- 这轮范围明显过大。
- 风险和回归面远超当前需求。

### 结论

采用方案 A：**一体化收口状态同步 + 文案表达**。

## 总体架构

这轮不新建一个独立子系统，而是在现有链路上补三层合同：

1. **formatter 合同**
   - question / permission / 自然中止 / retry 通知如何在微信里展示。
   - 这里解决：示例单独占行、选项说明、终结结果通知文案、retry 错误摘要。

2. **replyability 合同**
   - 哪些通知仍然可回复，哪些通知只能信息展示。
   - 这里解决：电脑端终结后的 qid / handle 回收、自然中止通知是否可回复。

   当前至少要明确写死这张矩阵：

   - `question(open)`：可回复
   - `permission(open)`：可回复
   - `question/permission terminal result`：信息型，不可回复
   - `ordinary retry/error`：信息型，不可回复
   - `natural-stop`：可回复

3. **状态同步合同**
   - 当 request / session 状态在电脑端变化时，微信侧如何同步得到终结原因或错误摘要。
   - 这里解决：旧入口回收、终结原因通知、retry 详情补齐。

也就是说，这次不是“单独改文案”，而是把**显示、可回复性、状态同步**一起收成同一条设计。

### 最小实现载体

这轮实现边界再补一层更硬的约束，避免 plan 阶段重新发明模型：

1. `ordinary retry/error` 与 `natural-stop` 都继续从现有 session / retry 采集链路进入 `collectNotificationCandidates`。
2. `ordinary retry/error` 最少要有这些持久化/渲染字段：
   - `sessionID`
   - `action/stage`
   - `redactedSummary`
   - `severityAdvice`
   - 且**永远不分配 handle**。
3. `natural-stop` 在此基础上额外必须带：
   - `handle`
   - `reply target identity`（至少能唯一定位到对应 session / instance）
4. `/reply` 必须新增一个只处理 `natural-stop` 的查找分支，不能把这类回复并入 question / permission request 状态机。
5. 旧 question / permission 第一次离开 replyable 集合时，必须在现有持久化真相源里保留一份可按旧 `qid / handle` 查询的 terminal metadata，至少包含：
   - `入口标识`
   - `固定终结原因`
   - `replacement 标识（如有）`
   - `terminalResultSent`
   后续 slash 拒绝与“terminal result 最多一条”的去重都只能复用这份 metadata，不能只依赖 open 集合或 cleanup 之后的残留状态。

## 设计细节

### 1. 回复示例改成逐行可复制

当前微信里长按更适合复制整行，所以所有可执行示例必须改成**单独占一行**。

适用范围：

1. question 的 `/reply ...` 示例
2. permission 的 `/allow ...` 示例
3. 自然中止通知里的自定义回复示例

合同：

1. 解释文字与命令示例不能混在同一行。
2. 一条示例就是一整行，允许用户直接长按复制。
3. 自然中止通知必须始终提供一条明确、可复制的回复示例，不能只告诉用户“你可以补充说明”却不给具体发法。
4. 这条自然中止回复示例本轮固定沿用 slash 语义，形态写死为：`/reply <handle> 你的补充内容`。
5. 这不是单纯格式建议，而是 formatter 层必须满足的展示合同。

### 2. question 选项展示“标题 + 说明”

如果原始 question prompt 为某个选项提供了说明文字，微信通知里就必须把它展示出来，而不是只剩标题。

合同：

1. 选项标题仍然保留编号和主标题。
2. 选项说明单独作为该选项下的一行文本展示。
3. 如果某个选项没有说明，只显示标题即可。
4. 不为了适配说明而牺牲原本的编号回复语义。

目标不是把选项展示成完整 UI 卡片，而是在纯文本约束下，让用户离开电脑也能判断区别。

### 3. 电脑端终结后，微信侧必须回收旧入口并说明原因

这是这轮最重要的 correctness 合同之一。

当 question / permission request 在电脑端进入终态时：

1. 对应 qid / handle 必须退出微信侧可回复集合。
2. 微信侧不能只是静默把旧入口吞掉；必须补一条终结结果通知。
3. 终结结果通知至少要写出：
   - 哪个 qid / handle 被回收
   - 回收原因
   - 微信侧若继续回复，为什么会被拒绝

本轮用户可见终结原因标签固定只允许：

1. 已在电脑端回复
2. 已在电脑端拒绝
3. 已过期
4. 已被新入口替代

这些原因不是内部枚举建议，而是用户可见的固定原因集合。终结结果通知与后续“已结束”拒绝提示必须复用同一组原因标签，不能一边写“已在电脑端拒绝”，另一边只写成笼统的“已结束”或“已处理”。

并且要补下面两条硬合同：

1. 对同一个被回收的旧 `qid / handle`，用户可见的 terminal result 通知**最多一条**，并且只在它**第一次离开 replyable 集合**时发出。
2. 后续 `cleanup / purge` 只能清理内部状态，不得再补发第二条 terminal result 通知。

如果同一个旧入口同时经历多重内部终结事件，用户可见原因标签的优先级固定为：

1. `已被新入口替代`
2. `已在电脑端回复`
3. `已在电脑端拒绝`
4. `已过期`

这里的 `recover / cleanup / replace` 统一只是内部触发事件，不得直接变成额外的用户可见原因标签：

1. `cleanup` 只能继承并复用更早的用户可见终结原因。
2. 只有在确实产生了新 `qid / handle` 时，才允许把用户可见原因提升为 `已被新入口替代`。
3. 如果没有新入口，就不能在用户文案里使用“已被新入口替代”。
4. terminal result 通知与后续 slash 拒绝提示都必须带出同一个新入口标识（若存在）。

### 4. 已终结入口再次回复时返回稳定“已结束”提示

当前问题之一是：目标 request 明明已经不存在，微信再回复却还会提示“已回复问题”一类成功文案。

这轮要求：

1. `/reply <qid> ...` 或 `/allow <handle> ...` 如果命中的是已终结入口，必须返回稳定中文提示。
2. 提示内容要明确它已经在电脑端结束，而不是继续冒充成功。
3. 这条提示与上面的终结结果通知要语义一致，不能一个说“已回复”，另一个说“已结束”。
4. 旧入口拒绝提示至少要同时包含三项：
   - 被拒绝的 qid / handle
   - 与终结结果通知一致的终结原因
   - 不再接受回复 / 需改看新入口的原因说明

### 5. Agent 自然中止升级成可回复通知

当前自然中止没有形成可操作闭环。用户要求在这类情况下允许直接发一条自定义回复。

这轮设计：

1. 自然中止不再只是一条信息提示。
2. 它会成为 session / retry 链路上的一个**可回复分支**。
3. 通知里必须明确告诉用户：
   - 它是自然中止，而不是普通 retry
   - 用户现在可以回复一段自定义文本
   - 具体可复制的回复示例是什么
4. 回复入口继续沿用 slash 文本交互，不引入按钮；本轮固定使用 `/reply <handle> 你的补充内容`。

这里不要求把自然中止包装成 question / permission；它仍然属于 session / retry 这条线，只是增加 replyable 语义。

为了避免和 question / permission handle 打架，本轮把 natural-stop handle 命名空间固定为 `s*` 前缀，例如 `s3`。

合同：

1. 一个 natural-stop handle 只能绑定一条 replyable natural-stop 通知。
2. 它必须能唯一定位到一个 reply target identity（对应的 session / instance）。
3. 它与 `q*` / `p*` 共享“当前活跃 handle 不得冲突”的总约束，但命名空间前缀不同。
4. 用户已回复或电脑端状态继续推进后，该 `s*` handle 必须失效，并返回与其终结原因一致的“已结束”提示。

natural-stop 失效后的用户可见原因集合本轮固定为：

1. 已在微信端补充回复
2. 已在电脑端继续处理
3. 已过期

后续 `/reply <s*>` 必须返回：

1. 该 `s*` handle
2. 上述固定终结原因之一
3. 不再接受回复的原因说明

本轮把 natural-stop 的终结合同固定为**不额外补发独立终结提示通知**；用户可见的终结反馈只要求在后续 `/reply <s*>` 拒绝时稳定返回。也就是说，这组原因标签只要求在 natural-stop slash 拒绝路径内保持固定，不能退化成“未找到 handle”或笼统失败。

### 6. retry / error 通知补足错误摘要

retry 通知必须把核心失败信息带到微信里，但不能把长堆栈原样复制过去。

合同：

1. 必须说明失败发生在哪类动作或阶段。
2. 必须说明脱敏后的短原因摘要。
3. 必须说明处理建议 / 严重度，当前至少从以下固定集合里选一类表达：
   - 可等待自动重试
   - 建议尽快人工查看
   - 已停止并等待你的回复
4. 不能直接泄漏冗长堆栈或敏感字段。
5. 如果原因无法安全展示，也必须明确写出“原因摘要不可安全展示”，而不是退化成一条泛泛的“有问题”。

这条线与现有 diagnostics / redaction 逻辑要保持一致，不再另造一套脱敏规则。

其中还要写死一条负向边界：

1. `ordinary retry/error` 的处理建议只能从 `可等待自动重试`、`建议尽快人工查看` 中选择。
2. 只有 `natural-stop` 才允许使用 `已停止并等待你的回复`，并同时附带 reply handle 与可复制示例。

### 7. 实现边界

为了控制范围，这轮采用最小扩展：

1. **question / permission 终结结果通知**
   - 不做成新交互系统。
   - 在现有 request / notification 同步链路里补一个终结事件分支。
   - 终结结果通知本身是信息型通知，不可再回复。

2. **自然中止可回复通知**
   - 不重做 session-error 整体模型。
   - 在现有 session / retry 通知分支里增加一类 replyable 自然中止语义。
   - `ordinary retry/error` 与 `natural-stop` 的用户可见字段矩阵必须明确区分，不能只靠 formatter 分支临时判断。

3. **formatter 收口**
   - 不拆新的微信模板引擎。
   - 继续在现有 question / permission / status / retry formatter 上增量收口。

## 测试策略

至少覆盖：

1. formatter 回归
   - question 选项标题 + 说明都能输出
   - 无说明的选项只输出标题，不产生占位空行
   - 所有 `/reply ...` / `/allow ...` 示例单独占一行
   - 自然中止通知也必须包含单独占一行的可复制 `/reply <handle> ...` 示例

2. 状态同步回归
   - 电脑端 reply / reject / expire / recover / cleanup 后，旧 qid / handle 会被回收
   - 微信侧随后再回复会得到稳定“已结束”提示
   - 微信会收到包含 `qid / handle + 终结原因 + 不再接受回复原因` 的回收通知
   - 旧入口拒绝提示与终结结果通知复用同一终结原因标签
   - 同一个旧入口的 terminal result 通知最多只发一条
   - `cleanup` 不会把更早的用户可见原因覆盖成新的顶层标签
   - 只有确实生成新入口时，才允许出现“已被新入口替代”标签，并同时带出新入口标识
   - 旧入口终结后的 slash 拒绝会复用持久化 terminal metadata，而不是因为 request 已被 cleanup 就退化成“未找到”

3. 自然中止回归
   - 自然中止会生成一条可回复通知
   - 微信自定义回复能沿既定 slash 入口进入后续处理
   - 通知里有固定的可复制 `/reply <handle> 你的补充内容` 示例
   - natural-stop handle 使用 `s*` 前缀，且不会与 `q*` / `p*` 活跃 handle 冲突
   - ordinary retry/error 不会错误地带出 handle、reply 示例或“等待你的回复”文案
   - natural-stop 失效后再次 `/reply <s*>` 会返回 `handle + 固定终结原因 + 不再接受回复原因`，而不是退化成“未找到 handle”

4. retry 详情回归
   - 通知同时出现 `失败动作/阶段 + 脱敏短原因摘要 + 严重度/处理建议`
   - 不会泄漏长堆栈或敏感字段

## 成功判定

满足以下条件才算完成：

1. 微信通知里的所有可复制示例都变成逐行独立展示。
2. question 选项如果有说明，微信里能同时看见标题和说明。
3. 电脑端终结 request 后，微信里的旧 qid / handle 会被回收，而且用户能看到明确的回收原因通知；该通知至少包含 `入口标识 + 终结原因 + 继续回复为何被拒绝` 三项。
4. 微信侧再回复已终结入口时，不再出现误导性成功提示，而是稳定告诉用户该入口已结束，并复用与回收通知一致的终结原因标签。
5. 对同一个旧入口，terminal result 通知最多只发一条；后续 cleanup / purge 不会再产生第二条用户可见终结通知，也不会覆盖原有原因标签。
6. Agent 自然中止会形成一条可回复通知，允许用户直接发自定义补充，并提供固定、逐行可复制的 `/reply <handle> 你的补充内容` 示例；该 handle 使用 `s*` 前缀并能唯一定位回复目标。
7. natural-stop 失效后再次回复 `s*` handle 时，用户会看到固定的终结原因与拒绝提示，而不是“未找到 handle”或其它临时 copy。
8. retry / error 通知会同时带出 `失败动作/阶段 + 脱敏短原因摘要 + 严重度/处理建议`，让用户离开电脑也能大致判断发生了什么；只有 natural-stop 才允许出现“等待你的回复”语义。
9. 整条线仍然保持在“微信通知状态同步 + 文案修订”范围内，没有扩大到其它子系统重构。
